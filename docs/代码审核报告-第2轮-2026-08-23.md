## 三、详细说明

### 1. 🔴 TTS 失败后问答对已写入历史，重试导致上下文重复

`voice_api.py` 当前顺序是：

```python
answer = llm_service.chat(messages)      # 3. LLM
conversation.add_user(sid, asr_text)     # 4. 写历史 ← 注释称"成功后才写入"
conversation.add_assistant(sid, answer)
audio = tts_service.text_to_speech(answer)  # 5. TTS ← 若在这里失败…
```

注释声称"成功后才写入历史，避免重试导致重复提问"，但 **TTS 排在写入之后**。TTS 失败（网络抖动、超长文本）→ 客户端拿到 500 → 重试同一句 → 历史里出现两对相同问答，污染多轮上下文。

**实测复现**（mock ASR/LLM/TTS，TestClient 调用）：

```
[2] TTS失败响应 -> 500
[2] 失败后历史(期望为空): [{'role':'user','content':'你好'}, {'role':'assistant','content':'你也好'}]
[2] 同句重试 -> 200
[2] 重试后历史: ['user:你好', 'assistant:你也好', 'user:你好', 'assistant:你也好']
```

**建议**：把两行 `conversation.add_*` 移到 `tts_service.text_to_speech(answer)` 成功之后、构造响应之前，真正兑现"全链路成功才记忆"的意图。代价是 TTS 失败时连 LLM 结果也不记忆——对语音助手这是合理取舍（用户反正没听到回答）。

### 2. 🔴 空/极短音频返回误导性 500

本地校验只查 `size > 0` 和 `< 10MB`（`audio_utils.py:13-27`），一个只有 WAV 文件头的假音频（112 字节）能通过校验，发到百炼后返回：

```
400 InternalError.Algo.InvalidParameter: The audio is empty
```

随后被 API 层兜底转成 **500「服务暂时不可用」**。用户以为服务器坏了，实际是自己没录上声音。这不是理论问题——`logs/app.log`（2026-08-18）和旧日志（2026-08-07 共 3 次）里反复出现同一报错，触发方式就是快速点按录音按钮产生近空 blob。

mock 测试同时证实：112 字节假 WAV 能一路通过本地校验到达服务层。

**建议三层配合**：

1. `asr_service.speech_to_text` 捕获上游 400 并翻译为业务错误，让 API 层映射成 400 而非 500：

   ```python
   except openai.BadRequestError as e:
       if "empty" in str(e).lower():
           raise ValueError("录音太短或没有听清声音，请再试一次")
       raise
   ```

2. `static/index.html` 的 `mediaRecorder.onstop` 加最短时长守卫（如 < 300ms 或无数据就不发请求），并在 UI 提示"好像没录到声音"。
3. 可选：`validate_audio` 对 < 100 字节的音频直接判空（WAV 头至少 44 字节，100 字节以内必然无声）。

### 3. 🟠 音频先整读后才校验大小

`file.file.read()` 把整个上传体读完才调 `validate_audio`。Starlette 对 > 1MB 的 UploadFile 会溢写磁盘临时文件，而 uvicorn 默认不限制请求体大小——恶意客户端可用超大 body 消耗磁盘/带宽，10MB 的上限拦不住"读取阶段"的资源消耗。

**建议**：加一个轻量中间件检查 `Content-Length` 请求头，超过 `AUDIO_MAX_BYTES + 余量` 直接 413；或在读取时按上限分块拷贝。

### 4. 🟠 OpenAI 客户端未设置超时与重试

`asr_service.py` 与 `llm_service.py` 的 `OpenAI(...)` 均用默认配置（超时长达 600 秒）。接口是同步路由、跑在线程池（默认 40 线程）里，上游一旦挂起，几十个并发请求即可占满线程池，拖垮整个服务。

**建议**：

```python
_client = OpenAI(
    api_key=settings.DEEPSEEK_API_KEY,
    base_url=settings.DEEPSEEK_BASE_URL,
    timeout=30,        # 或按服务分别设置
    max_retries=2,
)
```

### 5. 🟠 TTS 流式拼接依赖隐含假设

核对 `dashscope==1.26.5` 源码确认流式产出语义：

- 每个 sentence 事件产出一个**增量** chunk（`audio_url=None`）；
- `finish_reason=stop` 时产出最后一个 chunk，其 `audio_data` 是**前面全部增量的拼接**，`audio_url` 取决于服务端是否返回。

`tts_service.py:32` 用 `not chunk.audio_url and chunk.audio_data` 过滤，等于假设"finish 块必带 url"。实测当前服务端行为满足该假设（历史音频时长正常），**目前是正确的**；但若服务端某天在 stop 块不返回 url，整段音频会被再拼一遍（模拟验证过该退化路径）。另外注意：不能简单改用"块长等于累计长度则丢弃"的启发式去重——等长增量块会误判（已实测踩坑）。

**建议**（二选一）：改为 `stream=False` 拿 `audio_url` 后下载一次，语义最干净；或保留现实现并加注释明确该依赖假设，SDK 升级时重点回归此处。

### 6. 🟠 无限流（遗留）

鉴权挡住了无 Key 的调用，但持 Key 的调用没有频率限制，ASR/LLM/TTS 三条计费链路仍可能被脚本刷爆。对外部署前建议：反代层（nginx `limit_req`）或应用内加简单令牌桶（如 `slowapi`）。本地开发可暂缓。

### 7. 🟡 `.gitignore` 匹配不到滚动的日志文件

现有规则 `logs/*.log` 无法匹配 TimedRotatingFileHandler 生成的 `app.log.2026-08-07`（后缀不是 `.log` 结尾），git status 显示它处于未跟踪状态。改为：

```gitignore
logs/app.log*
```

### 8. 🟡 TTS 参数名与 SDK 形参不一致

`tts_service.py:23` 传的是 `format="wav"`，而 `HttpSpeechSynthesizer.call` 的形参是 `audio_format="wav"`。`format` 被 `**kwargs` 吞掉后又合并回 `input.format`，恰好值相同所以**碰巧正确**——但若未来新增 `TTS_FORMAT` 配置或传其他 kwargs，容易出现双键覆盖的隐性 bug。改为 `audio_format=settings.TTS_FORMAT` 即可。

### 9. 🟡 API Key 比较非常量时间

`x_api_key != expected` 建议换成 `secrets.compare_digest(x_api_key, expected)`，消除时序侧信道的理论风险。一行改动。

### 10. 🟡 `session_id` / `text` 无长度上限

两个接口都直接把外部字符串用作字典 key / 模型输入。建议各加合理上限（如 `session_id ≤ 64` 字符、`text ≤ 2000` 字符），超限返回 400。顺带一提：会话淘汰机制本身工作正常，此条只是减少被滥用时的浪费。

### 11. 🟡 工作区改动未提交

第 1 轮的修复分布在 6 个文件中尚未 commit，加上本报告。建议处理完本题 #1、#2 后一并提交，形成干净的版本节点。
